# ADR-0017: Portable tone/style guide (style-guide.json) for PR comment tone

**Status:** Accepted

## Context

PR comment tone matters — it sets the register of review conversation, and it's personal. One reviewer might prefer direct questions ("Is this safe?"), another might prefer collegial framing ("Worth checking: is this safe?"). Both are professional; they're just different voices. As reviewers use `/pr-comment-guide` to draft PR comments on a shared panel or at different times, tone consistency lets the project and the team speak in a recognizable voice.

Two problems block this today:

1. **No portable tone guide** — reviewers have personal style, but it lives in their heads or scattered across past reviews. There's no standard, portable, portable format for capturing "here's how I sound" so others can model on it or CI can reference it.
2. **No discovery** — even if someone wanted to adopt a team's review voice, discovering "what is the team's actual tone" requires reading through years of reviews by hand.

## Decision

### Two-layer cascade for tone

Tone is loaded via a two-layer cascade, separate from the reviewer-persona context cascade (ADR-0005):

1. **Personal style guide** — `~/.claude/style-guide.json` (hand-authored via `/generate-style-guide` or manual copying of `prompts/style-guide.json.template`, never auto-seeded)
2. **Default style guide** — `~/.claude/prompts/style-guide.json` (symlinked from this repo's `prompts/style-guide.json` via the existing `install.sh` mechanism)

This is a *separate* cascade from ADR-0005's reviewer-persona context cascade for a reason: tone is personal voice and transient (people's review style evolves), while personas are reusable archetypes and stable. A four-layer cascade on one dimension (reviewer context) is already managing complexity; adding a two-layer cascade on a different dimension (tone) keeps the two concerns orthogonal.

### Schema

Both files share the same JSON schema:

```json
{
  "version": 1,
  "source": "default" | "manual" | "generated",
  "generatedAt": null | "ISO-8601 timestamp",
  "scope": null | { "repos": ["owner/repo", ...] },
  "examples": ["real PR comment string", ...],
  "toneNotes": ["short freeform pattern note", ...],
  "_instructions": "optional, only in template for documentation"
}
```

- `examples` — 6-12 verbatim PR review comments, lightly trimmed but never rewritten, showing the full breadth of the reviewer's tone
- `toneNotes` — 3-6 short observations about what the examples have in common ("prefers questions," "no hedging," "names fixes directly," etc.)
- `generatedAt` and `scope` are non-null only for files generated by `/generate-style-guide`

### Install behavior divergence

Unlike `preferences.yaml` (auto-copied from its template on setup — see ADR-0005 amendment), `~/.claude/style-guide.json` is **never auto-seeded**. Here's why:

`preferences.yaml` is a lens on existing behavior — it helps reviewers emphasize/frame findings differently, but it doesn't prescribe new voice. If a user hasn't authored it yet, the template copy acts as a safe placeholder (the examples are generic enough that "not my preferences" is a safe default).

`style-guide.json` is different — it is literally "your tone" or "your team's tone." Auto-seeding it with someone else's examples would be a lie (it would claim the user's voice was something it wasn't). So we don't seed it. Instead:

- Setup creates a symlink from `~/.claude/prompts/style-guide.json` → the shipped default (so the cascade has a working default immediately, out of the box, for anyone who hasn't generated a personal one).
- Users who want a personal style guide either run `/generate-style-guide` (which analyzes their review history and asks for confirmation) or manually copy `prompts/style-guide.json.template` and edit it.
- The `_instructions` field in the template documents the schema and points to `/generate-style-guide` as an alternative to hand-authoring.

### The `/generate-style-guide` confirmation gate

`/generate-style-guide` is a command that searches the user's PR review history, extracts representative comments, distills them into examples and tone notes, and presents the draft to the user for confirmation before writing. This is the **load-bearing safeguard** — because the resulting file shapes how `/pr-comment-guide` models tone, and auto-appended machine files that influence review behavior must be human-reviewed first.

This is direct lineage from ADR-0007's lesson: this repo once tried an auto-appended `decisions.yaml` file and reverted it in favor of hand-authored/confirmed config. The philosophy is the same: machines can draft and propose, but humans confirm before a tool starts shaping review behavior.

### Why not in the reviewer-context cascade?

The reviewer-persona context cascade (ADR-0005) is four layers: global persona → project context → user preferences → per-reviewer local. Tone was not added as a fifth layer there because:

1. **Dimension mismatch** — reviewers are reusable across projects; tone is personal and transient.
2. **Loading pattern** — every reviewer loads its context on demand; tone is loaded once, globally, by `/pr-comment-guide`.
3. **Scope** — the context cascade is project-aware (`.claude/project.yaml` lives in the project, per-reviewer local overrides too); tone is user-global (at `~/.claude/`, not per-project).

A separate two-layer cascade is simpler and clearer than shoe-horning tone into the reviewer cascade.

### Note on `prompts/peer-merge.md` exclusion

The `prompts/peer-merge.md` prompt (`peer-merge` agent) is a latency-optimized, fast-path alternate to `/expert-review-coworker` (now deprecated in favor of `/expert-review <PR-URL>`). It applies peer tone directly as prose guidance without wiring into the `style-guide.json` cascade. This is deliberate: on a fast path, the prose rules are loaded inline and do not require file I/O or JSON parsing. The omission is not an oversight — it's a performance tradeoff documented explicitly in the prompt itself.

## Consequences

- **Good:** Tone is now portable and discoverable — users can share a `style-guide.json` with their team or fork a teammate's to learn from it. `/generate-style-guide` makes tone discoverable from review history without hand-authoring. The shipped default works out of the box; users are never blocked.
- **Good:** Tone is separate from reviewer personas and preferences, keeping each dimension focused.
- **Cost:** Three files could now hold tone-related data: `style-guide.json`, `preferences.yaml`, and reviewer persona bodies. Convention: genuine tone examples and patterns in `style-guide.json`, emphasis/framing lens in `preferences.yaml`, reviewer-specific guidance in persona YAML.
- **Constraint:** Since `style-guide.json` is loaded by `/pr-comment-guide` on every run, file I/O is unavoidable. But the cascade is two files max, so the cost is predictable.
